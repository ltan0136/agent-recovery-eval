# 架构与执行边界

本项目用于开发和检查工具调用系统的故障恢复与版本回归能力。核心是可重放的本地状态模拟、与状态独立的判定器，以及包含原始轨迹的结果包。它是命令行评测工程，不是托管 SaaS，也不声称生产级分布式系统保证。

## 1. 组件职责

| 组件 | 输入 | 职责 | 可见信息 |
| --- | --- | --- | --- |
| 案例生成 | 工作流、业务参数变体、调度种子、故障条件 | 冻结任务和故障调度，生成条件哈希 | 完整评测配置 |
| 状态模拟器 | 冻结案例和工具调用 | 校验操作参数、维护业务状态、注入故障、记录提交事件 | 状态、故障配置、调度队列 |
| 被测策略 | 业务请求、公开步骤计划、工具规范和公共返回 | 选择调用、查询、重试或停止 | 不含隐藏故障标签、评分答案或内部账本 |
| 可信判定器 | 所有迟到写入结束后的状态、提交账本和预期业务约束 | 检查完成、重复、缺失、关联与约束 | 只在评分阶段读取完整状态 |
| 版本比较 | 相同案例与条件哈希的两组结果 | 配对检查、回归定位、按案例簇估计不确定性 | 两组结果和冻结条件 |
| 报告与复现 | 原始结果、轨迹、运行元数据 | 输出机器可读证据、HTML 报告和重放入口 | 按运行记录呈现，不修补模型回答 |

## 2. 一次执行的生命周期

1. 根据工作流、参数变体、种子和故障条件生成一个案例。每次执行使用独立状态，禁止借用上一回合的写入结果。
2. 被测策略读取业务请求、公开计划和工具契约。公开计划规定业务步骤，因而本版主要测恢复和执行，不单独测从自然语言生成业务计划的能力。
3. 策略经公共工具接口调用状态模拟器。模拟器在预定位置触发故障；返回的超时不会直接暴露写入是否提交。
4. 策略到达完成条件、主动停止或预算上限后结束。模型调用失败与预算耗尽应保留在运行结果中，不能从总体统计中静默删除。
5. 判定前送达所有已安排的迟到写入，避免把“暂时没出现的重复”误判为没有重复。
6. 判定器读取最终状态和事件账本。策略自己的成功声明不等于成功判定。
7. 导出结果、原始轨迹和条件哈希。版本比较拒绝案例缺失、重复配对或条件不一致的数据。

## 3. 四种业务工作流

| 工作流 | 业务状态 | 关键检查 |
| --- | --- | --- |
| 工单与通知 | 工单及其关联通知 | 正确内容、通知关联、重复与缺失 |
| 库存与订单 | 库存占用、订单及确认 | 数量与库存约束、订单关联、重复占用 |
| 会议预约 | 时段预约及邀请 | 时段一致性、预约关联、重复预订 |
| 文档审核与发布 | 文档版本、审核及发布状态 | 版本匹配、审核先后约束、未审核发布 |

四种工作流有不同状态和业务约束，标识分别为 `ticket_dispatch`、`inventory_order`、`meeting_booking` 和 `document_publication`。它们并非四条完全相同的串行链：库存占用和创建订单可以独立开始，发货需要占用及扣款；会议的房间占用和创建会议可以独立开始，最终确认需要占用及邀请完成。服务端接受满足依赖的其他合法拓扑顺序。公开步骤按一种固定拓扑顺序列出，并不要求只能按这一个顺序执行。

业务参数变体不是新增工作流，故障条件也不是新增业务领域。具体操作名称以 `recovery_eval/workflows.py` 和导出的工具规范为准。

## 4. 故障语义

| 条件 | 含义 | 主要检查的恢复问题 |
| --- | --- | --- |
| 无故障 | 正常工具返回 | 是否具备基础执行能力 |
| 提交前超时 | 请求尚未产生业务写入即返回超时 | 是否恢复遗漏步骤 |
| 提交后丢响应 | 写入已经完成但调用方未收到结果 | 重试是否造成重复副作用 |
| 延迟提交 | 调用超时后原写入仍可能在之后完成 | 查询后重试是否与迟到写入竞争 |
| 陈旧查询 | 查询暂时看不到已发生的写入 | 是否把“未查到”当成确定未提交 |
| 重复投递 | 同一请求被重复送达服务端 | 是否具备稳定去重契约 |
| 限流 | 公共接口返回可重试的速率限制 | 是否有界等待及重试 |
| 永久失败 | 目标操作持续不可用 | 是否正确停止、报告失败并控制调用量 |

对应代码标识为 `clean`、`pre_commit_timeout`、`lost_ack`、`late_commit`、`stale_read`、`duplicate_delivery`、`transient_rate_limit` 和 `permanent_failure`。

故障由模拟器分阶段、人工安排。逻辑时钟只表示仿真顺序，不是互联网延迟分布。当前结果不能外推到真实网络、服务故障率或现实生产环境。

## 5. 策略、模型与传输分别是什么

1. **手写策略**：有界重试、查询后重试、稳定幂等键重试、不重试。它们是已知行为的基线，用于检查环境及判定器，不是 LLM 成绩。
2. **真实模型恢复**：`recovery_eval/agents.py` 的 `run_agent` 通过适配器让模型实际决定下一次操作。默认最多 8 次模型请求、12 次工具调用，允许一次明确记录且计入预算的格式重试。原始全文严格解析，不从混合文本中偷偷抽取正确 JSON。
3. **历史静态诊断**：`recovery_eval/local_model.py` 和 Prime 的旧诊断任务包读取既有最终状态并给出判断；这类结果不能标为真实工具恢复成绩。
4. **MCP stdio**：`python -m recovery_eval.mcp_server` 提供跨进程公共工具传输。`get_task` 读取公共任务和工具规范，`execute` 调用模拟工具，`finish` 只返回关闭状态；完整评分写入评测方指定的结果文件。真实客户端的传输测试不包含模型推理。详见 [MCP 说明](MCP.md)。
5. **Modal / Prime**：可选平台入口与核心引擎分开。`modal_eval.py` 调用 v0.2 引擎，支持手写策略批次及真实本地模型动作循环；Prime 的各任务包以自己的 README 声明测量对象。v0.1 静态诊断数据不能自动成为动态恢复成绩。云端是否真实运行以结果元数据为准。

稳定幂等键策略的优势来自服务端的幂等契约及策略是否正确使用它。它不能被解释为语言模型更聪明，也不能证明任意外部工具都支持恰好一次效果。

模型消息通过文本 JSON 动作协议传递，支持不具备原生 function calling 的模型。`basic` 和 `guarded` 提示条件使用相同公共工具与权限；后者强调稳定操作键、超时结果未知和重新查询证据。API 不返回 token ID 时记录为空，不伪造 token 计数。

## 6. 回归比较与证据链

比较必须匹配案例集合及完整条件哈希。工作流内的同一业务参数变体，在不同种子与故障条件下会产生相关结果。统计重采样因此以 `(workflow, variant_id)` 为簇，在两版本之间保留配对关系；不把每个回合都假定为独立新任务。

簇数太少时只提供描述性结果及“不足以下结论”的状态。故意把好策略换成差策略得到的回归，只证明比较流程能检出这类变更，不能写成真实模型升级退化事件。

当前 bootstrap 固定 500 次重采样、随机种子 0，默认 95% 百分位区间；不足 5 个明确案例簇时不计算区间。5 簇是工程保守门槛，达到门槛不代表统计结果充分稳定。`duplicates`、`missing` 或 `false_success` 在任一案例变差时阻止放行；模型接口错误保留在分母，若无更优先的安全阻断则返回 `inconclusive`。其余情况下根据完成率差区间与允许退化阈值给出 `pass`、`block` 或 `inconclusive`。

环境哈希覆盖案例、工具调用预算、幂等契约、引擎版本和结算规则。提示哈希、模型请求预算和采样配置也应一起审查；条件哈希相同并不自动说明模型配置相同。缺少费用或真实耗时的记录按缺失值保留，不按零费用或零耗时计入。

原始 JSONL、轨迹和哈希是审查依据。报告是对原始记录的展示。运行结束状态、失败原因、模型预算和代码版本应和结果共同保留，不能只提交筛选后的成功截图。

## 7. 代码导航

| 文件 | 作用 |
| --- | --- |
| `recovery_eval/workflows.py` | 工作流声明、参数变体、条件矩阵和配置哈希 |
| `recovery_eval/engine.py` | 状态模拟、公共工具、故障注入、判定和手写基线 |
| `recovery_eval/agents.py` | 真实模型适配器、严格动作协议、预算和生成记录 |
| `recovery_eval/regression.py` | 配对验证、簇 bootstrap、切片与门禁 |
| `recovery_eval/mcp_server.py` | 公共 MCP stdio 接口 |
| `recovery_eval/core.py`、`local_model.py` | 保留的 v0.1 模拟与静态诊断入口 |
| `modal_eval.py`、`integrations/` | 可选平台执行、任务包与集成说明；各包单独声明动态恢复或静态诊断范围 |

## 8. 当前工程边界

1. 使用合成业务和本地模拟状态，不向真实客户发通知，不执行付款，不连接真实生产数据库。
2. 不训练语言模型，不以规则基线冒充模型，不宣称提出新算法。
3. 不承诺外部模型接口可用、云端额度、真实部署吞吐或生产服务等级。
4. 扩展新业务时需要增加真正不同的状态与判定约束；只换几个标题不会增加业务覆盖。
5. 扩展真实系统前需要单独处理认证、数据授权、隐私、访问控制、清理与成本限制。
